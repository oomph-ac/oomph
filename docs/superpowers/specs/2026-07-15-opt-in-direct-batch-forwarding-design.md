# Opt-in direct batch forwarding

## Goal

Add an opt-in mode to Oomph's standalone proxy that preserves each inbound
gophertunnel network batch while processing its packets through Oomph, then
flushes the resulting outbound packets immediately. The existing 50 ms tick
batching remains the default.

Each forwarding direction otherwise adds a timing-dependent 0–50 ms wait.
Removing both waits reduces request/response ping by about 50 ms on average,
with an observed reduction between nearly 0 ms and nearly 100 ms depending on
flush-tick alignment.

This change applies only to `integration/proxy`. The native Dragonfly
integration has no proxy forwarding hop and remains unchanged.

## Public API

Add `Config.EnableBatchForwarding bool` to `integration/proxy.Config`.

When false, the proxy continues using `ReadPacket`, `WritePacket`, and the
existing Oomph tick flush. When true, the proxy enables gophertunnel batch
reading on its client listener and default backend dialer. A custom `Dial`
implementation may still be used, but the returned backend must implement the
batch-reading and order-preserving immediate-write capabilities required by
the mode. The proxy returns a descriptive error if it does not.

The optional capability is checked at runtime so enabling this feature does
not make a breaking interface change for existing custom backends.

## Processing and ordering

The client and backend loops read one complete network batch at a time. They
process packets sequentially in their original order through the same rewrite,
detection, cancellation, transfer, and state-tracking logic used today.

Surviving packets are collected and passed to `WritePacketImmediate` once per
input batch. That method appends them after packets Oomph already placed in the
destination send buffer and flushes the buffer immediately. This guarantees:

- packet order within each inbound batch;
- order between consecutive inbound batches;
- order relative to packets Oomph generated before or during handling; and
- no wait for the next 50 ms Oomph tick before forwarded traffic is sent.

The latency reduction is not a fixed 50 ms guarantee: it averages about 50 ms
across a request and its response because both forwarding directions
independently wait 25 ms on average in legacy mode.

An entirely cancelled batch still triggers an immediate flush so packets
generated by Oomph while handling that batch are not delayed.

`WritePacketDirect` is intentionally not used because it bypasses the existing
send buffer and could overtake an earlier Oomph-generated packet.

## Transfers and errors

When a backend batch contains a `Transfer`, packets before it are immediately
written to the client, the transfer is performed, and packets following it
from the old backend are discarded. This matches the current behavior, where
the loop switches to the new backend after reading the transfer packet.

Read, write, and capability errors terminate the session through its existing
error path. A stale backend generation remains ignored as it is today.

## Testing

Tests will cover both modes and prove that:

- the option defaults to the legacy single-packet path;
- enabled mode preserves packet and batch order in both directions;
- cancelled and transformed packets produce the expected outbound batch;
- buffered Oomph-generated packets precede forwarded packets;
- each processed batch is flushed immediately, including all-cancelled batches;
- transfer packets flush preceding packets and discard the old batch tail; and
- an enabled proxy rejects a custom backend lacking batch capabilities with a
  descriptive error.

## Dependency

Oomph will consume the gophertunnel revision containing PR #80. No additional
ordering change is required in that PR: `ReadBatch` preserves inbound order,
and the existing `WritePacketImmediate` provides outbound ordering.
